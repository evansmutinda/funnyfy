# User Guidelines & Communication Preferences

## Important Notes for Development Assistance

### User Background
- **User is NOT a programmer** - Detailed explanations are required
- **Non-technical user** - Technical concepts need to be explained in accessible terms
- **Learning-oriented** - Explanations should help understanding, not just provide solutions

---

## Communication Guidelines

### When Providing Code or Instructions:

1. **Explain Before Implementing**
   - Always explain WHAT the code does before showing it
   - Use simple analogies when possible
   - Break down complex concepts into smaller pieces

2. **Use Plain Language**
   - Avoid jargon without explanation
   - Define technical terms on first use
   - Provide context for why something is done a certain way

3. **Step-by-Step Approach**
   - Break tasks into clear, numbered steps
   - Explain each step's purpose
   - Check for understanding before moving forward

4. **Visual Aids When Helpful**
   - Use code comments liberally
   - Show file structure with explanations
   - Use simple diagrams or flowcharts when appropriate

5. **Ask Before Assuming**
   - Verify understanding before proceeding
   - Offer to explain further if needed
   - Don't assume prior knowledge

### When Explaining Technical Concepts:

- **Start with the "Why"** - Explain the purpose first
- **Then explain the "What"** - What it does
- **Finally explain the "How"** - How it works (simplified)
- **Provide real-world examples** - Connect to familiar concepts

### Code Comments & Documentation:

- **Heavy commenting** - Add comments explaining what each section does
- **Inline explanations** - Explain variables and functions clearly
- **File-level comments** - Explain the purpose of files/modules
- **Usage examples** - Show how to use code with examples

---

## Example: Good vs. Bad Explanations

### ❌ Bad (Assumes Technical Knowledge):
"Use Retrofit with OkHttp for networking, and implement a repository pattern with Flow for reactive data streams."

### ✅ Good (Explains Everything):
"We'll use Retrofit (a library that makes it easier to talk to web servers) and OkHttp (which handles the actual internet connection). Think of Retrofit as a translator that converts your app's requests into internet messages, and OkHttp as the postal service that delivers them. We'll use a repository pattern (a way of organizing code so all internet calls go through one place - like a receptionist who routes all calls) and Flow (a way of getting data that updates automatically when something changes, like a live TV feed instead of a photo)."

---

## Preferred Learning Style

- **Progressive disclosure** - Start simple, add complexity gradually
- **Practical examples** - Show real, working examples
- **Compare to familiar things** - Use analogies to everyday concepts
- **Questions welcome** - Encourage questions at any point

---

## What to Avoid

- ❌ Using acronyms without explaining them (e.g., "MVVM", "API", "UI")
- ❌ Jumping straight to code without explanation
- ❌ Assuming familiarity with tools, frameworks, or concepts
- ❌ Using technical shorthand without context
- ❌ Rushing through explanations

---

## What to Include

- ✅ Clear explanations of every technical term
- ✅ Step-by-step walkthroughs
- ✅ Plain language descriptions
- ✅ Real-world analogies
- ✅ Visual structure (indentation, comments, organized files)
- ✅ Context and reasoning for decisions
- ✅ Troubleshooting tips in simple terms

---

## Future Interactions Checklist

Before providing any code or technical solution:

1. ☐ Did I explain what this does in simple terms?
2. ☐ Did I explain why we're doing it this way?
3. ☐ Did I break it down into understandable steps?
4. ☐ Did I use plain language and avoid unnecessary jargon?
5. ☐ Did I provide context and examples?
6. ☐ Did I offer to explain further if needed?
